# Oh shit, Zombies. — report for Tom

Status: **scored runs finished 2026-11-02 08:33 CST.** 98 scored lives: 58 natural, 40 loud. The arm table below is generated by `player/tabulate.py` from each life's `summary.json`.

## 1. Load limits

Measured on this machine with headless bots that walk flat out and swing every few seconds, all in the same Chicago blocks. That's harsher than people. The app is limited to 1 CPU and 448 MB by the compose file, and other renders were running (load average 7 to 24).

**This machine holds 25 players comfortably; 30 is the edge, and it fails hard above that.** The failure is input lag: frames keep arriving while your presses wait in a queue, so it looks alive and plays dead. Memory isn't the limit (150 MB at 35 bots). CPU is: Python runs the game on one core, so more cores won't help without a redesign. Set `MAX_PLAYERS=25` before going public.

Bandwidth: about 6 kB/s per walking player on the wire, so 25 players is about 1.3 Mbit/s up, plus a burst of about 170 kB raw when a new set of buildings is sent.

Two server bugs found by this test, both fixed and committed on `public-hardening` as 9861352:
1. **A freeze anyone could trigger.** About 15 simultaneous `DELETE /api/me` calls held every database connection while queueing for the world lock, and the lock's owner needed a connection. The whole game stopped answering for minutes. Regression test added.
2. **Frame size.** Stashes went in every frame unchanged (10 kB), and walking re-sent every building outline (up to 165 kB) about twice a second. One walking player went from about 320 to about 70 kB/s raw.

## 2. The arm table

Setup, as fixed in DEVLOG.md before any arm ran: Chicago, 300 s limit, a new account each life, one life at a time, the world reset between lives, arms in shuffled blocks. Every arm sees the server 250 ms late. **Reflex delay: 250 ms, enforced in code (`player/core.py`, `REFLEX_S`).** The brain only ever reads the newest frame that is at least 250 ms old, and acts through the public websocket protocol (`pos`, `act`), like any player's client. It reads nothing from the server's memory or database.

The goal layer drags it down to e's level.

### Why the goal layer costs so much

It isn't the 3 s of thinking. The survivor carries on with a nearest-container errand while the planner thinks. It's what Haiku chooses: it chases chests and toolboxes for weapons, and those sit behind doors in other buildings. 12 to 14 Haiku goals per 10 lives timed out at 50 s, and goal arms stood still 47 to 59% of the time, against 26 to 28% for b and c. Sonnet chose more like the nearest-container rule and did better.

## 3. Recommended player design and cost per hour

**Scripts plus Jev, without a model choosing goals during play.** Code does walking, doors, looting and combat, reading the server 250 ms late. Jev, 3 to 4 times a second while zombies are in sight, judges fight, flee, go indoors or carry on. The errand is the nearest-container rule. Cost: **about $0.12 an hour** of Jev at the rates measured (about 48,000 input tokens a minute at $0.042 per million; output is free). An LLM is worth having for narration from the log afterwards and for an occasional "what next" when the survivor is idle and safe, not in the loop. If you want an LLM in the PLAN seat on camera, use Sonnet rather than Haiku: in 4 lives it lost less, though it's a hint, not a result. Measured full-stack costs: $0.23 an hour with Haiku (API-equivalent; it runs on the logged-in subscription), $1.42 an hour with Sonnet.

Honest framing for the video: scripts alone are already strong (1 death in 10, 1.3 damage per zombie). Jev didn't beat them by a margin this sample can show, though it never died, cost almost nothing, and was never late. It also has a blind spot: in 98 lives it never chose to bandage, and once let a bite bleed for two minutes. The model layers make better video than better survivors, which is roughly what I predicted.

## 6. What I did not check

- Real phones, real networks, and the path through a Cloudflare tunnel. Every load number is loopback.
- More than one start city under load at once, any soak of hours (memory growth, database size), and fetching new map regions from OpenStreetMap under load.
- Lives longer than five minutes. Infection turns you after 24 to 48 real hours, and five-minute lives never reach any of that.
- Whether a better Jev prompt would fix the bandage blind spot. The prompts were frozen before scoring, as promised; changing them is the next experiment, not this one.
- Statistical significance. These are 90% bootstrap intervals on 10 or 4 lives, and only 3 deaths in total. Treat small differences as noise.
- Manchester, and daytime for most of the sample. Blocks 0 to 6 were night.
- Codex cost per call (its CLI doesn't report it), and whether the local GPU box's one Qwen slot holds up while openclaw is using it. The slot was idle when I measured.
- Human reaction time for comparison. 250 ms is my claimed fair floor, not measured against people.
